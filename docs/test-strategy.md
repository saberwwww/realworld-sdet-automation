# 测试策略

## 范围与计数

正式收集 35 条 pytest 实例（包含参数化展开），27 API + 8 UI；其中5条标记 db，同一条用例同时观察两层结果，不能重复计数成40。故障注入文件仅显式执行，不计正式覆盖。

| 层次 | 场景与断言依据 |
| --- | --- |
| API 用户 | 正常注册/登录；非法邮箱、必填缺失、重复用户；错误密码、未知用户；状态、errors/user结构及业务字段 |
| API 鉴权 | 缺少Token、错误scheme、无效/格式错误JWT、签名篡改、过期、合法Token；分别验证契约和本地补丁明确错误码 |
| API 文章 | 创建/读取/更新/删除、字段校验、未登录、非作者权限、删除后404；不只检查200 |
| UI | 登录成功、错误密码、退出、发布、编辑、删除、游客编辑重定向、空标题提交；页面状态与业务结果 |
| SQL（5条重叠） | CRUD持久化；非法更新不改变记录；非作者修改/删除不改变记录（2实例）；UI编辑持久化 |

详细 UI 前置条件、步骤及预期见 test-design-ui.md。真实表为 articles_article、accounts_user；API description/body 对应 summary/content，title 更新可导致 slug 改变，删除为物理删除。查询按主键或唯一作者定位，检查记录总量，避免仅证明“某行存在”。

## 数据、隔离和诊断

- 每会话迁移新 SQLite，不读取普通开发数据库；每用例唯一用户/文章。
- 通过 API 准备/清理文章；清理时按作者查询当前 slug，兼容标题修改。
- SQLite URI mode=ro、SQL参数绑定、每次查询关闭连接；没有清空全库逻辑。
- UI使用官方插件和独立context、语义定位、expect自动等待；本地网络边界会拦截外部业务API。
- 清理记录验证文章剩余0、用户随临时库销毁、服务退出、context关闭和无残留Chromium。
- 断言失败保留JUnit具体用例与原因；UI额外保留截图和Trace。先分清产品、测试代码、环境问题。

## 验证策略

正式 fixed 全量、连续重复、反序；单独 baseline 验证BUG仍可被同一组断言检测；显式 diagnostics_demo 验证错误断言留下可诊断证据。并不将 baseline 或主动注入的红灯统计为正式全量通过。

CI运行同一套fixture，不另写一套服务启动流程。不用固定sleep判断服务可用，HTTP轮询有截止时间且检查进程状态。安装步骤 bash pipefail 防止 tee 掩盖失败，测试退出码保持非零，always仅保证尝试上传已有证据，不保证磁盘故障/强制取消仍能上传。

## 覆盖边界

未覆盖多浏览器、移动端、大规模并发、负载、完整安全渗透、所有社交功能、生产部署及PostgreSQL。35个实例是代表性风险覆盖，不能宣称业务全覆盖；一次通过也不是稳定性统计结论。GitHub Actions远程运行及Linux运行时状态以stage-5.md为准。
